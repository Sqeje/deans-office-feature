# Как расширять приложение

## 1. Добавление вертикального среза

1. Заполните SLICE_TEMPLATE. Зафиксируйте владельца данных, контракт, доступ, источник истины и общий код, который потребуется изменить.
2. Создайте серверный модуль в Modules/<Name>. Реализуйте IAppModule с уникальным Id: сервисы регистрируются в AddServices, маршруты — в MapEndpoints. Подключите экземпляр одной строкой в Infrastructure/AppModules.Create. Не помещайте бизнес-код в Program или Kernel.
3. Конфигурации IEntityTypeConfiguration размещайте рядом с сущностями модуля. AppDbContext подхватывает их автоматически. Используйте Set<TEntity>() либо добавьте необходимый DbSet. Новую миграцию создавайте после обновления от main; применённую историю не меняйте.
4. Frontend-модуль экспортирует FrontendModule. Подключите его в modules/sections. Страницы и их запросы остаются в папке модуля. Общая оболочка сама создаёт маршруты и навигацию; существующие StudentHome/ProfilePage показывают пример.
5. Обновите типы `npm run api:generate`, используя работающий API. Используйте shared/api.ts и client из него; CSRF обязательно перед каждой мутацией. HTTP 401 означает отсутствие сеанса, 403 — недостаточный доступ; не подменяйте 403 повторным входом.

Серверный тест ProbeModule в IdentityTests показывает регистрацию сервиса и маршрутов, fallback-авторизацию, политику и проверку конкретной группы. Это тестовый образец, не production endpoint.

## 2. Доступ и запись

Для операции сотрудника укажите `.RequireAuthorization(Permissions.ScheduleWrite)` и перед чтением/записью вызовите `guard.Require(Permissions.ScheduleWrite, entity.UniversityId, entity.GroupId, ct)`.

Если объект ищется по ID, сначала ограничьте поиск университетом из ICurrentActor; проверьте группу найденного объекта. Не проверяйте группу из тела запроса вместо фактической принадлежности записи. Для переноса записи между группами нужны права на обе группы. Не выдавайте весь университет при отсутствии GroupId.

Для операции студента требуйте роль Student, непустой actor.StudentId и фильтры `StudentId == actor.StudentId && UniversityId == actor.UniversityId`. Общая роль Staff не даёт доступа к студенческому профилю.

Запишите значимое изменение через `await audit.Record("requests.status_changed", request.Id.ToString(), ct)`, затем сохраните данные и аудит одним SaveChanges. Операция должна быть константным машинным кодом, EntityId — идентификатором, без содержания заявки. При нескольких сохранениях используйте явную транзакцию с commit только после успеха всех действий.

Новое разрешение требует изменения Permissions.All/IsUniversityWide, соответствующей проверки БД StaffGrants новой миграцией, документации и тестов. Универсальные произвольные строки разрешений из клиента не поддерживаются. Назначение существующих прав — контролируемая серверная процедура; демо-seed не является механизмом управления реальными сотрудниками.

## 3. Подключение университетского источника

Адаптер размещается в модуле-потребителе, например Modules/Schedule/Integrations. Он реализует ISourceAdapter и IExternalSource<RawLesson>, преобразователь — IRecordInterpreter<RawLesson, NormalizedLesson>, применение — IImportApplier<NormalizedLesson>. RawLesson/NormalizedLesson определяет модуль расписания; Kernel их не знает.

Зарегистрируйте stateless-адаптер как singleton ISourceAdapter; он не должен захватывать DbContext или scoped-сервисы. Для HTTP используйте фабрику HttpClient. Преобразователь и applier со scoped-зависимостями живут в scope операции. Секреты получайте из серверной конфигурации соответствующего OptionsSection; они не входят в DTO и журналы.

Конфигурация связывает код адаптера с источником конкретного университета:

```json
{
  "Integrations": {
    "Bindings": [{
      "UniversityId": "10000000-0000-0000-0000-000000000001",
      "Capability": "schedule",
      "SourceId": "primary",
      "AdapterId": "university-schedule-api",
      "OptionsSection": "Sources:UniversitySchedule"
    }]
  }
}
```

Пример намеренно не включён в рабочие настройки: без зарегистрированного адаптера приложение откажет при старте. Реальные адреса и ключи передаются через серверное окружение, например Sources__UniversitySchedule__ApiKey.

После проверки `sources.manage` для текущего университета получите binding через `registry.Get(actor.UniversityId, "schedule", "primary")`; `registry.Resolve(binding)` возвращает зарегистрированный адаптер. Конструируйте ImportPipeline из соответствующих трёх типизированных этапов. Не выбирайте университет из запроса без проверки полномочий. Фоновый запуск в будущем получает явно проверенный сервисный контекст, не создаёт фиктивный HTTP-сеанс.

Fetch получает binding и cancellationToken; транспорт ограничивает объём ответа и время чтения. Интерпретатор проверяет каждую запись и сопоставляет внешние ключи по `(UniversityId, SourceId, ExternalId)`. Сопоставление по ФИО и угадывание группы запрещены. Версия внешней схемы валидируется адаптером; несовместимая версия — ошибка интерпретации, а не попытка угадать поля.

Pipeline сначала преобразует весь ограниченный пакет; лишь затем вызывает applier один раз. Он проверяет дубликаты ExternalId, размер пакета и отмену между этапами. ImportResult различает FetchFailed, InterpretationFailed, ApplyFailed, Cancelled и Succeeded, возвращает безопасный ErrorCode и счётчики. Он не хранит результаты запусков и не запускает автоматические повторы.

**Обязанности applier, проверяемые тестами конкретного среза:** транзакция на пакет; уникальный ключ внешнего сопоставления; upsert без дубликатов; проверка UniversityId всех ссылок; откат всего пакета при ошибке; отсутствие удаления по отсутствию записи. Pipeline не может гарантировать откат произвольного чужого кода. Ошибка после фиксации транзакции не должна сообщаться как откат: applier возвращает успех сразу после commit, а отмена после commit не отменяет выполненное изменение.

Записывайте SourceId/ExternalId и время успешного получения в импортируемой модели. Поля источника не меняются ручными операциями; локальные записи помечаются отдельно. Удаление, ручные поправки поверх импорта, объединение нескольких источников и push обратно в университет требуют отдельного решения среза. Тестовый пример трёх этапов — ImportTests.

## 4. Контракты между модулями

Если Requests нужен список групп, Identity предоставляет узкий интерфейс чтения с фильтром UniversityId; Requests использует его через DI. Не передавайте DbContext или EF-сущности через этот интерфейс. Проверку вызывающего пользователя выполняет прикладная операция, университет передаётся явно. Не создавайте интерфейсы «на будущее» без потребителя.

Ошибки наружу: Problem Details с `code`, `traceId`, `status`; для общей ошибки используйте KernelHttp.Problem. Бизнес-валидация выбрасывает InputValidationException со словарём «поле → безопасные сообщения», общий обработчик возвращает 400 с errors и code=validation_failed. Не включайте персональные значения в эти сообщения. Нельзя отдавать Exception.Message, SQL, URL с токеном и stack trace. Для обращения в поддержку показывайте пользователю traceId.

Коды разрешений передаются как PermissionCode с фиксированными строковыми значениями. FrontendModule.permission типизирован этим enum из сгенерированного OpenAPI; опечатка не проходит сборку. Изменение кодов — изменение общего контракта с обновлением типов и тестов, не локальная строка внутри среза.
