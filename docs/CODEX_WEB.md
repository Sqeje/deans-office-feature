# Работа в Codex Web

Локальный запуск описан в [README](../README.md). Здесь описан порядок для отдельной облачной среды: она не использует Docker, `.env` и процессы с вашего ПК. Открытие `https://localhost` на вашем компьютере не открывает сайт из облачной задачи.

## Подготовка среды один раз

1. Подключите репозиторий к доступной вашей команде облачной среде Codex и выберите нужную ветку. Убедитесь, что в ней присутствуют `dev.ps1`, `compose.check.yaml` и актуальные инструкции: локальные неопубликованные изменения из чужого ПК в облако не попадают.
2. Попросите агента проверить инструменты приведённым ниже промптом. Не считайте наличие команды `docker` доказательством работающего Docker Engine.
3. Если доступны Docker Engine, Compose и PowerShell (`pwsh`), основной путь такой же: `pwsh -File ./dev.ps1 doctor`, затем `pwsh -File ./dev.ps1 check`. Для запуска приложения: `pwsh -File ./dev.ps1 up`.
4. Если Docker недоступен, агент проверяет возможность штатного запуска .NET SDK 10, Node.js 24 и отдельной PostgreSQL по [LOCAL_ENVIRONMENT.md](LOCAL_ENVIRONMENT.md). Нельзя заменять PostgreSQL на SQLite или обходить авторизацию ради проверки.
5. Если среда позволяет сохранять настройки подготовки, сохраните проверенные шаги установки зависимостей для следующих задач. Не сохраняйте пароли в репозитории или общедоступных скриптах.

Настройки облачных сред могут отличаться у участников. Официальная инструкция по повторно используемым средам: [OpenAI — Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments). Доступность инструментов, сети и браузерного просмотра необходимо проверить в конкретной задаче.

## Промпт для подготовки и диагностики

```text
Подготовь эту облачную среду для работы с проектом.
Прочитай AGENTS.md, README.md, docs/ARCHITECTURE.md, docs/AUTOMATION.md
и docs/CODEX_WEB.md. Сначала ничего не меняй в продуктовом коде.
Проверь текущую ветку, доступность Docker Engine (не только CLI), Compose,
pwsh, .NET SDK 10, Node.js/npm, PostgreSQL и браузерных инструментов.
Если Docker и pwsh доступны, выполни штатный dev.ps1 doctor и check.
Если нет — настрой доступный штатный путь без Docker по LOCAL_ENVIRONMENT.md,
используя отдельную одноразовую PostgreSQL для тестов. Не трогай рабочую БД.
Зависимости устанавливай в разрешённых пределах среды. Не меняй стек ради запуска.
Сообщи фактические команды, результаты, недоступные проверки и точную причину.
Не печатай пароли, connection strings с паролями, cookies и токены.
Не публикуй код, не пушь и не разворачивай внешние сервисы без моего разрешения.
```

## Промпт перед работой над срезом

Используйте основной [SLICE_START_PROMPT.md](SLICE_START_PROMPT.md), добавив:

```text
Мы работаем в Codex Web. До реализации проверь среду по docs/CODEX_WEB.md.
Срез № <номер>: <описание и демонстрация приёмки из docs/SLICES.md>.
Сначала подготовь план. Отдельно укажи, какие проверки сможешь выполнить здесь,
как проверишь работу UI с API и что потребуется проверить человеку.
После согласования плана реализуй срез и выполни доступные проверки.
Проверки, которые не запускались, явно отметь как не выполненные.
```

## Как посмотреть результат

Попросите агента запустить приложение и проверить доступный в среде браузер/preview. Если есть ссылка для просмотра, агент должен проверить её и объяснить, какие порты и сервисы за ней доступны. Не обещайте публичную ссылку только потому, что сервер запущен на облачном localhost. Для входа нужны API и PostgreSQL, а не только frontend preview.

Если доступного просмотра нет, сохраните отчёт выполненных тестов. После разрешённой передачи изменений участник с Docker получает ту же ветку и выполняет `dev.ps1 up` и `check`. GitHub Actions также проверяет код после разрешённой отправки в GitHub; это не автоматическая публикация сайта. Preview-деплой каждой ветки пока не настроен.

Пароли демо-аккаунтов создаются в `.env` именно той среды, где выполняется запуск. Они могут отличаться от паролей на компьютере товарища. Не просите агента выводить их в общий чат.
