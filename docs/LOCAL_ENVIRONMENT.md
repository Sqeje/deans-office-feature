# Локальное окружение Windows и новые чаты

Основной воспроизводимый путь — [AUTOMATION.md](AUTOMATION.md): Docker и команды dev.ps1 up/check. Ниже описан запасной путь разработки непосредственно в Windows, если Docker пока недоступен или нужен hot reload.

На машине, где создавался фундамент, SDK установлен в `.tools/dotnet`, а не в системный PATH. Каталог `.tools` игнорируется Git и не появится у товарища после clone. На другом компьютере установите .NET SDK 10 по требованиям README. Node.js 24 и npm также должны быть доступны.

Перед командами .NET в PowerShell из корня проекта выполните:

```powershell
& .\scripts\Enter-DevEnvironment.ps1
dotnet --version
dotnet build backend/Dean.Api/Dean.Api.csproj
```

Скрипт выбирает доступный SDK 10, при необходимости использует `.tools/dotnet`, и меняет PATH/DOTNET_ROOT только текущего процесса. Если используется локальный SDK и существует `.tools/nuget`, подключает этот кеш. Системные настройки и профиль пользователя не изменяются. При отсутствии SDK выводится ошибка, а не сообщение о готовности.

Каждый новый терминал нужно настроить заново. В инструментальных вызовах агента отдельные команды могут запускаться в новых процессах: запускайте скрипт **в том же вызове**, что и команды dotnet, либо используйте полный путь к SDK. Изменение окружения одного завершённого процесса не настраивает следующий.

## EPERM при npm ci и отсутствующий tsc

На Windows работающий Vite может удерживать `lightningcss.win32-x64-msvc.node`. `npm ci` переустанавливает node_modules; если операция прервалась, каталог может остаться неполным. Тогда отсутствие tsc — следствие незавершённой установки, а не повод устанавливать TypeScript глобально или менять package.json.

1. Остановите Vite этого проекта через Ctrl+C в терминале, где выполняется `npm run dev`. Не завершайте все процессы node: среди них могут быть другие приложения и агенты.
2. Дождитесь завершения других установок зависимостей в этом каталоге. Не выполняйте `npm ci` одновременно из двух чатов. Для параллельной работы используйте отдельные рабочие каталоги/checkout.
3. В каталоге frontend выполните `npm ci`. Проверьте код завершения; после неуспешной установки не запускайте сборку как будто зависимости готовы.
4. После успешной установки выполните `npm run build`, затем при необходимости `npm run dev`.

`npm ci --offline --no-audit --no-fund` допустим при полном локальном кеше. Если пакет не закеширован, этот способ не сработает: требуется обычная установка с доступом к registry. Не удаляйте lock-файл и не отключайте TLS-проверки ради установки.

Если установка всё ещё выдаёт EPERM, изучите точный путь и журнал npm. Причиной могут быть права песочницы, другой процесс или защита файлов. Если доступно штатное повышение разрешений, повторите необходимую команду через него. Не обходите отказ автоматической проверки разрешений и не меняйте глобальные права каталогов вслепую.

## Проверка браузером

После восстановления зависимостей запустите frontend и проверьте доступность localhost:5173. Для полного сценария входа backend и PostgreSQL также должны работать; `/health` должен возвращать успешный ответ. Пароли берутся из вашего серверного окружения, а не придумываются по имени аккаунта.

Команды Playwright и переменные DEMO_PASSWORD1, DEMO_PASSWORD2, DEMO_STAFF_PASSWORD приведены ниже в этом документе. При установленном Chrome можно указать CHROME_PATH. Браузерные тесты сами запускают Vite; не переустанавливайте node_modules во время их выполнения. Проверки API/сборки не подменяют проверку UI в браузере.

## Команды запуска без Docker

### Требования и запуск

Если dotnet отсутствует в PATH, используйте подготовку окружения, описанную выше. Все команды ниже выполняются из корня репозитория.

Нужны .NET SDK 10, Node.js 24 и PostgreSQL 17. `docker compose up -d db` запускает БД без опубликованного порта; для локального API используйте собственную локальную PostgreSQL или временный Compose override с привязкой `127.0.0.1:5432:5432`.

PowerShell, из корня:

```powershell
$env:ConnectionStrings__Database='Host=localhost;Database=dean;Username=dean;Password=<ваш-пароль>'
$env:Demo__Enabled='true'
$env:Demo__Password1='<первый-пароль>'
$env:Demo__Password2='<второй-пароль>'
$env:Demo__StaffPassword='<пароль-сотрудника>'
dotnet tool restore
dotnet run --project backend/Dean.Api -- --initialize
$env:ASPNETCORE_ENVIRONMENT='Development'
dotnet run --project backend/Dean.Api --urls http://localhost:8080
```

Во втором терминале: `cd frontend`, `npm ci`, `npm run dev`; откройте http://localhost:5173. Vite проксирует /api на API. HTTP допустим только в локальном Development; публичное развёртывание использует HTTPS.

### Проверки

```powershell
dotnet build backend/Dean.Api/Dean.Api.csproj
$env:TEST_DATABASE='Host=localhost;Database=dean_test;Username=dean;Password=<пароль>'
dotnet test backend/Dean.Api.Tests
cd frontend
npm ci
npm run build
```

TEST_DATABASE должна быть отдельной пустой БД для каждого прогона. Тесты не удаляют пользовательскую БД. CI создаёт одноразовую PostgreSQL. Контракты клиента обновляются командой `npm run api:generate` при работающем API.

Браузерная проверка: при запущенном локальном API задайте DEMO_PASSWORD1, DEMO_PASSWORD2 и DEMO_STAFF_PASSWORD равными паролям созданных аккаунтов. В frontend выполните `npx playwright install chromium`, затем `npx playwright test`. Тест сам запустит Vite и проверит два студенческих аккаунта, сотрудника, публичную часть и старые ссылки на ширине 360 px. Для установленного Chrome можно вместо скачивания Chromium задать CHROME_PATH полным путём к chrome.exe.
