# Архитектура

React → same-origin REST API → ASP.NET Core → PostgreSQL. Caddy завершает TLS. Один модульный монолит, DbContext и последовательность EF-миграций. Kernel задаёт общие правила выполнения; предметные модели и бизнес-правила находятся в модулях.

| Область | Ответственность |
|---|---|
| Kernel | Контекст пользователя, разрешения, регистрация модулей, HTTP-ошибки, аудит, контракты источников |
| Identity/Profile | Аккаунты, университеты, группы, профили и назначения прав |
| Schedule | Занятия, аудитории, расписание и его источники |
| AcademicPerformance | Оценки, зачёты, экзамены и их источники |
| Requests | Заявки и история обработки студентом/сотрудником |
| Notifications | Объявления, персональные уведомления, прочтение |

## Основные данные

ApplicationUser — аккаунт Identity с одним UniversityId. StudentProfile — необязательный студенческий профиль с ключом UserId: прежние ID студентов сохранены. Staff — роль аккаунта, отдельного пустого профиля сотрудника нет. Роли Student и Staff могут сочетаться; пользователь не может назначить их себе. Институты/факультеты и переключение университетов в этот этап не входят.

Внутренние идентификаторы университета и группы — UUID; Identity/StudentId — непрозрачные строки. Все связи персональных данных включают UniversityId. Составные FK запрещают связать пользователя, профиль, группу или назначение прав из разных вузов. Внешний ID имеет смысл только вместе с UniversityId и SourceId.

Серверные моменты времени — DateTimeOffset, UTC, JSON ISO 8601. Учебный календарь нельзя вычислять из часового пояса браузера: модуль расписания должен отдельно определить локальную дату и IANA-зону источника/университета. Enum/статусы принадлежат модулю, их контракт публикуется через OpenAPI; свободные варианты одного статуса в разных клиентах запрещены. Обязательность и ограничения полей задаются в DTO, проверках модуля и БД.

## Доступ

ICurrentActor загружает аккаунт, роли, профиль и разрешения из БД один раз на HTTP-запрос. Из cookies берётся удостоверенный UserId, из параметров клиента — только объект действия, не доверенный контекст. Отзыв роли/разрешения действует со следующего запроса.

Разрешения requests.manage, schedule.write, grades.write выдаются на конкретную группу; announcements.publish и sources.manage — на университет. Наличие роли Staff не даёт разрешений автоматически. Для маршрута используется политика разрешения, для конкретных данных — AccessGuard.Require с университетом/группой целевого объекта. Политика сама по себе не проверяет принадлежность объекта. Проверка студента дополнительно требует его StudentId и UniversityId в выборке.

API защищено fallback-политикой; публичные endpoints помечаются AllowAnonymous. Cookies HttpOnly/SameSite=Strict, Secure в production. Мутации /api требуют CSRF, включая вход. После входа перед мутацией запрашивается новый токен. API возвращает Problem Details с code и traceId; X-Request-ID связывает ответ с журналом. Исключения не раскрывают клиенту детали; в общем обработчике журналируются тип исключения и traceId, без его текста.

AuditWriter добавляет запись о значимом действии сотрудника в текущий DbContext. Модуль сохраняет изменение и аудит вместе. Если операция использует несколько SaveChanges, её владелец открывает явную транзакцию. Адаптеры не пишут предметные таблицы. Запись аудита не заменяет проверку прав. Журнал не содержит произвольных DTO, паролей и полного содержания заявок.

## Подключение и взаимодействие

Backend-модуль реализует IAppModule: AddServices и MapEndpoints. Единственный явный список — Infrastructure/AppModules. Конфигурации сущностей IEntityTypeConfiguration автоматически подхватываются из сборки API. Новый проект/сборка требует явного расширения списка сканируемых сборок; динамических плагинов нет.

Frontend-модуль экспортирует FrontendModule с pages, area, path, title, Page и необязательным permission. Реестр проверяет уникальность модулей и маршрутов. Оболочки /student и /staff используют общий сеанс; /applicants публична и не хранит заявления. Старые /app/* перенаправляются на /student/*. Общие UI-состояния и API-клиент находятся в shared, компоненты — в components/ui.

Модуль владеет интерфейсом возможностей, которые предоставляет соседям. Интерфейс регистрируется через DI; межмодульные DTO отделены от EF-сущностей. Прямая запись в таблицы другого модуля и циклические зависимости запрещены. Общую шину событий и универсальный репозиторий не вводим.

Получение внешних данных → интерпретация/сопоставление → применение модулем. Реестр подключений разделён по университету, возможности и источнику. ImportPipeline выполняет только ограниченный пакет в текущем процессе; транспорт, преобразование и атомарное сохранение реализует конкретный срез. Импортированные поля принадлежат источнику, локальные записи редактируются сотрудником. Нет удаления по отсутствию в ответе. Ошибка источника оставляет предыдущие данные. Планировщик, реальные адаптеры и UI настройки пока отсутствуют.
