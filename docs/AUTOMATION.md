# Одна команда для запуска и проверки

Первый запуск, установка, отличие образа от контейнера и FAQ: [README](../README.md). Облачная работа: [CODEX_WEB.md](CODEX_WEB.md). Здесь описаны детали автоматизации.

Один раз установите и запустите Docker Desktop с Linux containers (Windows) или Docker Engine с Compose plugin (Linux). Для dev.ps1 нужен PowerShell: Windows PowerShell 5.1 либо PowerShell 7; на Linux запускайте через `pwsh -File`. Системный .NET, Node.js и PostgreSQL для этого пути не требуются.

На Windows скрипт также ищет Docker Desktop в стандартных пользовательском и системном каталогах, если текущий чат был открыт до установки и ещё не получил новый PATH. Docker Desktop/Engine должен быть запущен; установка приложения сама по себе не запускает контейнеры проекта.

Первой сборке требуется свободное место для образов и кеша. Docker Desktop по умолчанию хранит WSL-данные на C:, даже если проект расположен на D:. При необходимости перенесите хранилище через Settings → Resources → Advanced → Disk image location на диск с запасом места и примените изменения. При ошибке input/output error сначала проверьте свободное место; не повторяйте загрузку на заполненный диск.

Из корня проекта:

```powershell
.\dev.ps1 doctor  # Проверить Docker Engine и Compose
.\dev.ps1 up      # Собрать и запустить приложение
.\dev.ps1 check   # Проверить текущий код в отдельном окружении
.\dev.ps1 status  # Состояние приложения
.\dev.ps1 logs    # Последние журналы
.\dev.ps1 down    # Остановить приложение, сохранив БД
```

## Что происходит автоматически

`up` использует существующий compose.yaml: PostgreSQL → миграции и демо-аккаунты → API и Caddy с frontend. При первом запуске создаёт `.env`, генерируя четыре разных случайных пароля. Заполненные настройки сохраняются, значения CHANGE_ME заменяются. Пароли в консоль не выводятся: они находятся в игнорируемом Git файле `.env`. Не удаляйте этот файл, чтобы не потерять соответствие настроек сохранённой БД. Повторный seed не меняет пароли существующих аккаунтов.

Откройте SITE_ADDRESS из `.env`, по умолчанию https://localhost. Для локального TLS один раз потребуется доверить сертификат Caddy/его локальный корневой сертификат. Для публичного домена используйте DEPLOYMENT.md. `up` не создаёт сервер, домен или доступ из интернета самостоятельно.

У запуска через dev.ps1 своё имя Compose-проекта, связанное с рабочим каталогом. Ранее запущенный вручную Compose-проект автоматически не переносится: его БД сохраняется отдельно. Не удаляйте старые тома и не запускайте две копии Caddy на портах 80/443; перенос нужных данных выполняется отдельно.

Вход: student1@demo.invalid, student2@demo.invalid, staff@demo.invalid. Пароли соответственно Demo__Password1, Demo__Password2, Demo__StaffPassword из `.env`.

`check` создаёт уникальный временный Compose-проект. В нём:

1. PostgreSQL с отдельными пустыми БД тестов и демонстрационного API.
2. Образы с .NET SDK 10, Node.js 24 и Chromium из установленной lock-файлом версии Playwright.
3. Release-сборка API, проверка соответствия миграций модели и серверные тесты.
4. Инициализация отдельного API, проверка health, сборка frontend и сравнение типов с OpenAPI.
5. Браузерные тесты студента, сотрудника, публичной области и сеанса.
6. Сохранение отчётов в artifacts/checks/<идентификатор> и удаление только временных контейнеров/данных проверки в finally.

Проверки не публикуют порты, не используют БД запущенного приложения и не монтируют host node_modules. Работающий Vite на Windows не удерживает файлы внутри образа. Исходники копируются в образ: команда не переписывает код, lock-файл или сгенерированные типы в рабочем каталоге. Изменённый контракт API сначала нужно обновить обычной командой api:generate в своей ветке; check только обнаруживает расхождение.

Образы и слои Docker кешируются. Первый запуск требует интернета и заметно больше времени/места; последующие используют кеш неизменённых слоёв. После изменения кода запустите up заново для пересборки; этот режим не предоставляет hot reload. Для быстрой разработки с Vite вне контейнеров остаётся LOCAL_ENVIRONMENT.md.

## Правила для команды и агентов

- Общая команда проверки — `dev.ps1 check`. GitHub Actions вызывает тот же сценарий, а не собственный набор команд.
- Сначала `doctor`; при недоступном Docker укажите конкретную причину. Не объявляйте контейнерную проверку успешной по DryRun или тестам PowerShell.
- `check -DryRun` только показывает команды, не создаёт `.env` и ничего не запускает. Тесты скриптов: `scripts/Automation.Tests.ps1`.
- Проверка сравнения контрактов на Windows/Linux: `node --test tools/check/schema-text.test.mjs`. Она проверяет нормализацию CRLF/LF, но не запускает контейнеры.
- При вынужденной работе без Docker используйте штатный локальный путь и явно перечислите недоступные проверки. Не переустанавливайте host node_modules ради контейнерного check.
- Параллельным участникам нужны отдельные каталоги clone/worktree. У check разные контейнеры и отчёты; каждому up нужен свободный набор портов 80/443. Не запускайте несколько копий приложения на одних портах и не завершайте чужие процессы.
- `down` не удаляет тома приложения. Удаление БД приложения, Docker prune, сброс .env и публикация не входят в автоматизацию.
- После аварийного завершения процесса/компьютера finally может не выполниться: временный проект будет виден в Docker с префиксом dean-check-. Его можно удалить отдельно после проверки имени; не чистите все Docker-ресурсы глобально.

Контейнерный путь должен пройти полный прогон на машине с Docker. Пока Docker недоступен, возможны только проверки логики скриптов и статических конфигураций; это не заменяет сборку образов и запуск тестового стека.
