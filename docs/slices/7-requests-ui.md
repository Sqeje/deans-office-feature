# Срез 7 — интерфейс заявок

## Цель и границы

Студент создаёт справку об обучении и заявление на индивидуальный график: заполнение → проверка → демонстрационное подтверждение с номером → подробности. Открывает примеры submitted, in_review, ready, rejected. Это frontend-этап: API, сохранение, история обработки и сотрудник остаются срезу 8; уведомления — срезу 10. Никаких мутаций API, миграций, новых зависимостей и изменений прав.

## Согласованный план

1. Изолировать срез в feature/07-requests-ui от незавершённой ветки 02. Вести план и статус в этом файле.
2. Типизированные демонстрационные данные и статусы принадлежат Requests; формы: место предъявления (обязательно, до 200 символов), экземпляры (целое 1–5); причина (обязательно, до 2000), начало и окончание периода (обязательны, окончание не раньше начала). Пробельные строки пустые.
3. Список с номером, типом, датой и статусом; мобильные карточки. Подробности содержат поля, причину отклонения либо пояснение демонстрационного результата. В готовом примере нет фиктивного скачивания.
4. Проверка перед подтверждением, редактирование сохраняет ввод, повторное подтверждение заблокировано. Номера ДЕМО-, даты подачи ISO UTC, отображение ru-RU/Europe/Moscow, период — календарные даты.
5. Только память: переходы сохраняют данные, перезагрузка, выход и смена пользователя сбрасывают. Примеры вымышлены, постоянная пометка демо. Никакого browser storage и подмены ошибок API.
6. Главная использует узкий контракт Requests и тот же пример; новая запись видна на главной. Переход в конкретный ID.
7. Типизированная фикстура loading/empty/error/send-error, валидация, повторы, 360 px и компьютер; сборки/серверные/браузерные тесты через dev.ps1 check; самопроверка и независимое ревью; текст PR без commit/push.

## Реализация и подключение

Владелец модели: frontend/src/modules/requests. RequestInput — discriminated union certificate/statement; DemoRequest содержит id, number, title, status, submittedAt, input и результат/причину. DemoSource предоставляет load/create; это демонстрационный контракт, а не API. Карта статусов едина для раздела и главной. Локальные данные отделены от представления.

RequestsSessionBoundary внутри существующего SessionProvider очищает память на смене ключа UniversityId/UserId ; ключ владельца перемонтирует только страницу Requests, не общую маршрутизацию или Login. Нового механизма сеанса нет. Доверие данным и серверная фильтрация не имитируются: студент видит вымышленные примеры, не настоящие персональные записи.

Навигация через существующий FrontendModule `/student/requests`: `?view=create` и `?requestId=…`; неизвестный ID показывает сообщение и возврат. Query-вариант вместо предлагаемого DESIGN `/:requestId` записан в DESIGN. Это избегает изменения реестра/меню. Staff-заглушка сохранена.

Общие изменения: App.tsx — подключение модульной границы сеанса; StudentHome/homeDemo — источник и ссылка Requests; README — актуализация состояния, DESIGN — маршрут. Kernel, API, schema.d.ts, Program.cs, AppDbContext и зависимости не изменяются. Токены и примитивы существующие; локальный CSS уточняет статус, чтобы общий старый зелёный badge не перекрывал варианты.

Визуальный стандарт: DESIGN §§5–7,12–18. Референсы не открывались: текст достаточен. Использованы Button, StatusBadge, SectionCard и существующая оболочка. Загрузка имеет собственную геометрию/текст, поскольку общий skeleton содержит текст об успеваемости.

## Как воспроизвести

Войти студентом, открыть «Заявки» → «Создать заявку». Заполнить справку, нажать «Проверить», при необходимости «Редактировать», затем «Подтвердить демонстрацию». Открыть заявку по выданному ДЕМО-номеру. Повторить для заявления с причиной и периодом. Вернуться к списку и открыть каждый статус. На главной новая запись должна совпасть с подробностями. Перезагрузка возвращает исходные примеры.
