# Requests

Модуль владеет локальными заявками студента и неизменяемой историей обработки. Регистрация через RequestsModule/IAppModule в AppModules. UI: /student/requests?view=create и ?requestId=UUID; /staff/requests и ?requestId=UUID.

API: GET/POST /api/requests/student, GET /student/{id}, GET /student/summary (204, если заявок нет); GET /staff/groups, GET /staff?groupId=UUID, GET /staff/{id}, POST /staff/{id}/status. Все пути относительно /api/requests. DTO и RequestStatus публикуются через OpenAPI; клиент генерируется штатной командой.

Создание принимает operationId (UUID) и input: certificate (place 1–200, copies 1–5) либо statement (reason 1–2000, start/end календарные даты). Пробелы по краям удаляются; поля другого вида запрещены. Повтор operationId того же студента/вуза с тем же нормализованным содержимым возвращает прежнюю заявку; с другим — 409. UI сохраняет ключ незавершённой отправки в query operationId, без содержания заявки. При обновлении страницы поля нужно заполнить повторно; повтор отправки по этому URL сохраняет ключ. Новый переход «Создать заявку» начинает новую операцию.

Номер — глобальная последовательность PostgreSQL identity, пропуски допустимы. UUID — внутренний идентификатор. Группа фиксируется на момент подачи, поэтому перевод студента не переносит прежние заявки к другому сотруднику. UTC-моменты отображаются ru-RU/Europe/Moscow, периоды — календарные даты.

Статусы: submitted → in_review → ready или rejected. Конечные статусы не переоткрываются. Отклонение требует причины до 2000 символов. Смена принимает version для optimistic concurrency; конфликт — 409. Заявка, история и общий аудит сотрудника сохраняются атомарно; общий аудит не содержит текста обращения.

Студент получает только свои данные в своём университете. Сотрудник требует requests.manage и AccessGuard по фактической группе заявки. Identity читается через IStudentDirectory. Мутации требуют CSRF. Демонстрационные записи из среза 7 используются только явными тестовыми фикстурами; production не подменяет ошибки API.

Документы, вложения, отзыв/редактирование заявок, источники и уведомления в этот срез не входят. Срез 10 может ссылаться на постоянный requestId через существующий requestDetailsUrl; отдельного механизма событий пока нет.
